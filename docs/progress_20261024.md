## 追加：BakaSU「动态管理器」为什么不能用

### 机制

BakaSU 的动态管理器**不按包名认管理器，按 APK 签名**：

```
管理器 → supercall DYNAMIC_MANAGER_OP_SET(size, sha256)
内核   → dynamic_manager.is_set = 1; track_throne(0)
       → 扫 /data/app，is_manager_apk() 用动态签名匹配
       → crown_manager(apk, uid_data, KSU_SIGNATURE_INDEX_DYNAMIC_MANAGER=255)
```

好处：管理器可以改包名、改签名（伪装/隐藏），内核照样认。

### 我们这边挡住了它

1. **`mgr_dont_invalidate=1`（补丁默认）** —— `apply_mgr_pkgs.py` 把
   `ksu_invalidate_manager_uid()` 包进了开关，默认关掉。
   动态管理器换签名时要**作废旧管理器 uid** 才能顶上去，这一步被禁掉了 ⇒ 新管理器永远加不上冕。
2. **`mgr_pkgs` 收紧成单包名** —— loader 在运行时把白名单钉成用户选的那一个包名，
   而动态管理器的包名是任意的 ⇒ 不在白名单里。
3. **手工 `ksud debug set-manager <pkg>`** —— 把 appid 钉死在固定包名上，
   之后换成改名/改签名的管理器就不认了。

### 解法（已实现，无需重编 ko）

ko 里三个参数/开关都在（`kernelsu_custom.ko` / `kernelsu_sukisu.ko` / `kernelsu_finasu.ko`
都能 grep 到 `dynamic_manager` + `mgr_dont_invalidate`），所以只改脚本层：

| 位置 | 行为 |
|---|---|
| marker `/data/local/tmp/route/m6/DYNAMIC_MGR` | 存在即进入动态管理器模式 |
| `_mgr_pin` | 有 marker ⇒ 不收紧 `mgr_pkgs` |
| `_mgr_selfheal` | 有 marker ⇒ 跳过单包名自愈 |
| `_mgr_crown` | 有 marker ⇒ 跳过手工加冕，交给内核 `track_throne` |
| insmod 参数 | 有 marker ⇒ 追加 `mgr_dont_invalidate=0` |

App 侧加了开关：管理器卡 → **「动态管理器」** 一行，点一下建/删 marker（状态显示「开 · 按签名」/「关」）。

### 限制

- `kernelsu_next.ko` / `kernelsu_ksu331.ko` 里**没有** `dynamic_manager`（上游没这功能），
  选这两家时开关无效，只能按包名认。
- 动态签名只存在内核内存，**重启后要重设**（管理器打开时自己会再设一次）。

## 追加（2026-10-24 真机定位）：SukiSU「需要更新内核」的真因不是 uapi

设备实测（`com.sukisu.ultra` 已选）：

```
[自编ko] 管理器=com.sukisu.ultra ⇒ 首选 kernelsu_sukisu.ko
⚠ 跳过自备 ko：kernelsu_sukisu.ko（md5/大小与打包清单不符）
⚠ 跳过自备 ko：kernelsu_custom.ko（md5/大小与打包清单不符）
⚠ 跳过自备 ko：kernelsu_finasu.ko（md5/大小与打包清单不符）
mode=OS9-SELX11 (module=kernelsu-os9-selx11.ko ...)
```

三份 uapi5/6 的 ko **全被判成「自备 ko」踢掉**，最后回落到 os9-selx11（**uapi4**），
SukiSU 管理器一看 `managerUAPIVersion(6) > kernelUAPIVersion(4)` ⇒ 弹「需要更新内核」。
root 照样成功（os9 也发 su），所以看起来"越狱成功但有告警"。

### 根因：`cut -d' ' -f2`

`bundled_ko.md5` 的格式是 `md5<8 空格>size<2 空格>name`。原实现：

```sh
_want_sz=$(echo "$_line" | cut -d' ' -f2)   # ← 第 2 个字段是空串！
```

空串永远不等于 `wc -c` 的实际字节数 ⇒ `return 1` ⇒ **每一份 ko 都被拒绝**。

### 第二个坑：ko_patch 就地改 ko

`dc_ksu` 的 `ko_patch` 直接改 `$RD/kernelsu-*.ko` 的 symtab（写 SHN_ABS，随 KASLR 变），
所以同一份 ko **下一次启动必然 md5 不同、大小不变**。即便修好上面那个 cut，
md5 严格比对也会在下次开机把自家 ko 全当外人。

### 修法（1.7 / vc7）

```sh
while read -r _m _s _n; do            # 内建 read 按空白切词，不依赖 cut/awk 的空格假设
  [ "$_n" = "$_b" ] && { _want_md5=$_m; _want_sz=$_s; break; }
done < "$RD/bundled_ko.md5"
[ "$_want_sz" != "$_got_sz" ] && return 1   # 以字节数为准
# md5 不同但大小一致 ⇒ 只提示「ko_patch 就地改过」，放行
```

真机（非模拟）验证，直接用设备自带 sh 跑同一个函数：

```
OK   kernelsu_sukisu.ko
OK   kernelsu_custom.ko
OK   kernelsu_finasu.ko
OK   kernelsu_ksu331.ko
OK   kernelsu_next.ko
  [ko] kernelsu-os9-selx11.ko 大小一致但 md5 不同（ko_patch 就地改过）⇒ 放行
OK   kernelsu-os9-selx11.ko
拒绝 junk(正确)
```

### 现状

- 设备上装的是 **1.7 (vc7, release 签名)**，md5 `ecd6c5ea7d18d2fcb4f9796ccf1a884d`
- 但**本轮仍跑 os9(uapi4)**：`run.lock` 的 boot_id 等于当前 boot，模块已加载，
  `ksud unload` 必 panic ⇒ 只能**重启后重新提权**才会加载 `kernelsu_sukisu.ko`
- 重启+重提后日志应出现：`mode=CUSTOM-OVERRIDE (module=kernelsu_sukisu.ko)` 和
  `[uapi] ko=kernelsu_sukisu.ko uapi=6 / 管理器=com.sukisu.ultra uapi=6 ✓`

## 追加（02:11 boot 9e27504c）：ko_patch2 覆盖不全，SukiSU ko 仍装不上

```

M6_VERDICT: ROOT   （modules=0 root=1 physrw=1 permissive=1）
```

`loadko_result.log`：

```
[ko_patch] slide=0x17e9a00000
[ko_patch] sym file: 250 entries
[ko_patch] STILL UND: down_read_trylock / __get_free_pages / dentry_path_raw /
                      free_pages / __arm64_sys_unshare / sort / bsearch / _raw_write_lock …
[ko_patch] 19 symbols still UND - ABORT (add to sym list)
```

**ko_patch2 是「一个符号没覆盖就整体 ABORT、且不写文件」**。SukiSU 的 ko 比 BakaSU 多引用
19~21 个符号（`down_read_trylock` / `free_pages` / `sort` / `bsearch` / `_ctype` /
`__per_cpu_offset` / `__cpu_possible_mask` …），250 条的清单不够 ⇒ 整轮作废 ⇒
`commit_creds` 没被补成 SHN_ABS ⇒ load_ko 仍然因 1 个未解析符号 abort。

### 补齐清单（不靠设备端算术）

设备 sh 的 `$(( ))` 实测会按 32 位溢出（`0xf3c017c0` 被当负数），
在设备上「live 减 slide」算不出正确的静态地址。改为**在主机上一次性算好**：

1. `adb exec-out cat /proc/kallsyms` 落盘（426,976 条）
2. `slide = live_init_task - 0xffffffc00a2017c0`（本 boot `0x17e9a00000`，与 ko_patch2 打印一致）
3. 对 5 份 ko 的全部 UND 符号，缺的补 `static = live - slide`
4. 校验：原清单 250 条里 249 条用同样公式算出来**逐字相等**（剩 1 条是 kallsyms 里没有的
   `commit_creds`，本来就靠清单），说明基准 `0xffffffc00a2017c0` 正确
5. 清单 250 → **271 条**，suksisu(253)/finasu(238) 的未定义符号**全覆盖**

ko_patch2 改成对**副本**操作（`.run_<name>.ko`）：它是就地改（写 SHN_ABS + 本 boot slide），
直接改原件的话下次开机会在已加 slide 的值上再加一次，地址全错。
