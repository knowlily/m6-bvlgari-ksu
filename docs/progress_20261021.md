## 1. 结论先行

管理器（`me.weishu.kernelsu` 3.3.1）显示「未安装」，**不是** UI 缓存、
也不是版本号不匹配，而是它**拿不到内核 fd**：

```
dispatcher 死（sys_call_table 写不进去）
  → ksu_handle_setresuid() 永不执行
  → 管理器进程没有 [ksu_driver] fd
  → scan_driver_fd() 扫不到 → ioctl 失败 → get_version()=0
  → Natives.isManager=false → ksuVersion=null → 首页「未安装」
```

判断依据（直接读 3.3.1 源码）：

| 位置 | 关键代码 |
|---|---|
| `HomeViewModel.kt:50` | `val ksuVersion = if (isManager) Natives.version else null` |
| `HomeMaterial.kt:201` | `val notInstalled = !ksuActive && state.kernelVersion.isGKI()` |
| `cpp/jni.cc:74` | `Java_..._isManager → is_manager()` |
| `cpp/ksu.cc:136` | `is_manager()` 走 `ioctl(fd, KSU_IOCTL_GET_INFO)`，fd 由 `scan_driver_fd()` 在 `/proc/self/fd` 里找 `[ksu_driver]` |
| `kernel/hook/setuid_hook.c:29` | `ksu_handle_setresuid()` → `if (is_uid_manager(new_uid)) ksu_install_fd();` |

也就是说：**管理器拿到 fd 的唯一入口是 setresuid 系统调用钩子**。

## 3. 新方案：kprobe 走同一条业务逻辑

关键点：这条路径**不需要拦截、不需要改返回值**，只要「setresuid 被调用时
顺便执行一段逻辑」，kprobe 的 pre_handler 天生能干这件事。

`patch/apply_sc_inject.py` 现在会在 `kernel/hook/arm64/syscall_hook.c` 末尾追加：

```c
extern int ksu_handle_setresuid(uid_t old_uid, uid_t new_uid);

static int ksu_sp_setresuid_pre(struct kprobe *p, struct pt_regs *regs)
{
    struct pt_regs *real = (struct pt_regs *)regs->regs[0];   // syscall wrapper 的 x0 = 真 pt_regs
    unsigned int euid = (unsigned int)real->regs[1];
    if (euid == 0xffffffffu) return 0;
    ksu_handle_setresuid(current_uid().val, (uid_t)euid);
    return 0;
}
static struct kprobe ksu_sp_setresuid_kp = {
    .symbol_name = "__arm64_sys_setresuid",
    .pre_handler = ksu_sp_setresuid_pre,
};
```

并在 `ksu_syscall_hook_init()` 末尾调 `ksu_sp_hooks_init();`。

为什么可行：`register_kprobe` 在本机已验证可用（reboot kprobe 早就注册成功，
`KernelSU: reboot kprobe registered successfully`）。
`__arm64_sys_setresuid` 在设备 kallsyms 里存在（`ffffffee7ab94964`）。

验证点（出包后在 kmsg 里找）：

```
ksu: setresuid kprobe rc=0
KernelSU: install fd for manager: 11207
```

## 4. 顺带修掉的真 bug：自愈守护跑在 kernel 域

logcat 里成片：

```
avc: denied { getattr } for path="/data/data/me.weishu.kernelsu/files"
     scontext=u:r:kernel:s0
```

`_mgr_selfheal` 的守护进程继承的是 **kernel 域**（rootshell 换 cred 之后），

（dmesg 里 `audit_lost=6545` 就是它）。

改成 `/dev/su -c "chown -R …; restorecon -R …"`（落在正常 su 域），
间隔 1s → 3s。

## 11. 「超级用户无实权」根因

App 提权链路（`kernel/feature/sucompat.c:161`）：

```
app: execve("su")
  → [execve 钩子] ksu_handle_execve_sucompat()
        · uid 在 allowlist
        · override_creds(ksu_cred) 打开 KSUD_PATH，装成临时 fd
        · 把这次 syscall **改写**成 execveat(fd, "", argv, envp, AT_EMPTY_PATH)
        · escape_with_root_profile()
  → ksud 以 root 运行
```

这套动作必须**替换 `sys_call_table[__NR_execve]`** 才能做（改参数 + 直接调另一个 syscall）。
我们的 dispatcher 写不进去 → 钩子不存在 → App 的 `su` 在内核里根本没被识别，直接 ENOENT；
管理器里"已授权"只是写 allowlist，不产生提权动作。

对照：管理器「正常」只依赖 `setresuid` 钩子（`ksu_install_fd`），我们已用 kprobe 补回；
App 提权依赖 `execve` 钩子（`escape_to_root`），这一条还空着。

## 12. 为什么不把 setresuid 的 kprobe 招数套到 execve

| 方案 | 结论 |
|---|---|
| kprobe 里直接 `escape_with_root_profile()` | ✗ `prepare_creds()` 是 GFP_KERNEL，kprobe 在禁抢占的原子上下文 → `BUG: sleeping function called from invalid context` |
| 只改 filename、不换 cred | ✗ App 无权 open `/data/adb/ksud`（DAC+SELinux）；`/dev/su` 对 untrusted_app 的可执行性未验证；KSU 正因此才用 `override_creds` + `execveat` |
| kprobe 里嵌套 `execveat` | ✗ 外层 syscall 帧悬空，稳定性不可接受 |

⇒ 回到根问题：让 `sys_call_table` 真正写进去。

## 13. 第三写入口：线性别名 + kimage_voffset

实测：`sys_call_table = ffffffee7b730a80`（紧跟 `_etext=ffffffee7b730000`，属镜像 `.data`）、
`kimage_voffset = ffffffee7bceb008`（`D` 符号，loader 从 `/proc/kallsyms` 现取地址）。

改动（`patch/apply_sc_inject.py`）：

```c
_va = (unsigned long)&ksu_syscall_table[ksu_dispatcher_nr];
_ph = phys_from_virt(_va & PAGE_MASK, &err);              // 原路径：页表走查
_ph_k = _va - *(unsigned long *)ksu_kimg_voff_addr;       // 新：内核自己的 VA→PA 偏移
if (_ph_k) _ph = _ph_k;
WRITE_ONCE(*(syscall_fn_t *)(phys_to_virt(_ph & PAGE_MASK) | (_va & ~PAGE_MASK)),
           (syscall_fn_t)ksu_syscall_dispatcher);
```

理由：镜像用 2 MB block 映射 + KASLR，页表走查容易在 block 项上算错物理地址；
`.data` 在线性映射里可写（不像 fixmap 可能被固定只读）。

新增模块参数 `kimg_voff`，loader 侧：

```sh
_kv=$(grep -m1 -w "kimage_voffset" /proc/kallsyms | cut -d' ' -f1)
_kp="$_kp sc_table=0x$_sct sc_ni=0x$_sni${_kv:+ kimg_voff=0x$_kv}"
```

三条写入口都会打印诊断，判据：

```
ksu: phys walk=0x… err=… kimg=0x…
ksu: linear alias=… pa=0x…
ksu: linear after write slot=42 val=…      ← 等于 dispatcher 地址就成功
KernelSU: sys_execve su found              ← App 的 su 被拦到
KernelSU: allow root for: <app uid>        ← App 拿到 root
```

构建：`39542425053`（v3.3.1）/ `39542435416`（Next 3.4.2）/ `39542445898`（BakaSU main），状态 in_progress。
若线性别名仍失败，日志会同时给出 `walk` 与 `kimg` 两个物理地址，可直接区分「地址算错」还是「写入被保护拦掉」。
