# 2026-10-28 · 档位化（targets.json）+ os11 目标 + 产物自校验

## 起因

要支持 MagicOS 11（110 固件，内核 `6.1.157-android14-11-g84ffa64b710b`），
但仓库里「编哪个内核」这件事散在 workflow 的 6 个 input 里：

```
ksu_repo / ksu_ref / ksu_tarball / sublevel / localversion / source_url
```

加一个固件就要人肉记住 `157` + `-android14-11-g84ffa64b710b` + 另一个 537 MB 源码 zip，
错一个字符就是 vermagic 对不上、内核直接拒载（而且现场只看到「Unknown symbol」或管理器一句「需要更新内核」）。
另外产物下载 → 改名 → 拖进 payload → 重算 md5 这四步也一直靠手。

## 改了什么

### 1. 唯一真源：`config/targets.json`

```json
"m6":   { "kernel_build": "g7d3922fade43", "localversion": "-android14-11-g7d3922fade43", ... }
"os11": { "kernel_build": "g84ffa64b710b", "localversion": "-android14-11-g84ffa64b710b",
          "source_var": "HONOR_SRC_URL_OS11", "artifact_suffix": "_os11",
          "config": "config/device-os11.config", "config_fallback": "config/device.config" }
```

`config/managers.json` 同步把「管理器 ↔ 上游仓库 / tag / uapi / 包名」也固化了（9 个：ksu331 / next /
sukisu / suki421 / finasu121 / finasu110 / finasu / basu420 / custom）。

### 2. workflow 只认 `target`

- 新增 input `target`（默认 `m6`，向后兼容）；
- `sublevel` / `localversion` 改成**可选覆盖**（留空 = 用 targets.json）；
- 源码地址按档位选 `HONOR_SRC_URL` / `HONOR_SRC_URL_OS11`（仓库变量，缓存 key 也按档位分开，
  不会把 10 的 zip 喂给 11 的树）；
- 「收集 ko」之后**自校验 vermagic**：不符直接让 job 失败（以前是人肉看日志）；
- artifact 名带档位后缀：`ksu-ko-<alias>_os11-<ref>`；产物里附 `md5sums.txt`。

### 3. 两个小工具

| 工具 | 干什么 |
|---|---|
| `tools/target.py` | `list` / `resolve --target os11`（输出 KEY=VALUE 给 GITHUB_ENV）/ `vermagic --target --ko` / `matrix --targets --managers`（生成 CI 矩阵 JSON） |
| `tools/ci_ko.py` | `pull --target os11 [--run id] [--alias x] [--sync]`：从 Actions 拉产物 → 改名 `kernelsu_<alias>_os11.ko` → 校验 vermagic/ELF/体积 → 落进 `m6-jailbreak-core/payload/os11/` → 可选跑 rebuild_manifest；`status --target` 列出本地 ko 与档位对不对得上 |

产物目录指向**兄弟仓库** `m6-jailbreak-core`（载荷真源在那边），不再各留一份。

## 实测（本机）

```
$ python tools/target.py vermagic --target os11 --ko ../m6-jailbreak-core/payload/os11/kernelsu_v325_os11.ko
OK  kernelsu_v325_os11.ko  368544B  vermagic=6.1.157-android14-11-g84ffa64b710b

$ python tools/target.py vermagic --target m6 --ko ../m6-jailbreak-core/payload/os11/kernelsu_v325_os11.ko
FAIL … want 6.1.157-android14-11-g7d3922fade43 / got …g84ffa64b710b   (rc=1)

$ python tools/ci_ko.py pull --target m6 --run 40281648326 --dry-run
  [dry] kernelsu_finasu121.ko → payload/kernelsu_finasu121.ko      # 真实 artifact 走通
```

## 待办

1. 配仓库变量 `HONOR_SRC_URL_OS11`（MagicOS 11.0.0.110 对应的 Bvlgari 源码 zip）。
   **没有它 os11 档编不了**，这是唯一的外部依赖。
2. `config/device-os11.config` 还没抓：现在 `resolve` 会回退到 `config/device.config`（m6 那份）。
   正确做法是把 110 机器连上，跑 `scripts/get_config.sh` 取 `/proc/config.gz`，存成 `device-os11.config`。
   两份 config 若真有差异（新固件常加 driver），回退版编出来的 ko 的 `__versions` 会大面积 CRC 不一致
   —— CI 的 check_crc 会直接暴露，不会静默装上。
3. 有了源码 + config 之后，跑 8 个 manager × os11 的矩阵，`ci_ko.py pull` 回灌，
   再按 `docs/08-os11-route.md` 上机验证。
