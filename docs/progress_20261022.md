# KernelSU on BVL-AN16 —— su 重定向（2026-10-22 阶段归档）

承接 `progress_20261021.md`。上一阶段停在：「管理器正常，但 App 授权后拿不到真 root」，
根因是 execve 钩子必须改写 syscall，而 `sys_call_table` 在 MagicOS 10 / BVL-AN16 上被 EL2 保护，
三条写入口（fixmap / set_memory_rw / 线性别名直写）全失败，第四条 `vm_map_ram` 也在 3.16.8 实测为**静默不落地**。

## 1. 结论：不走 sys_call_table，改双 kprobe

KSU 原生 `sucompat` 是「表钩子 + `escape_with_root_profile()`」，我们拆成两步，两步都能挂 kprobe：

| 步骤 | 钩子 | 干什么 |
|---|---|---|
| ① 换目标文件 | kprobe `do_execveat_common` | `filename == /system/bin/su` 且 uid 在 allowlist → `kstrdup(su_path)` 换掉 `fn->name` |
| ② 换身份 | kprobe `begin_new_exec` + kretprobe `security_bprm_committing_creds` | 改 `bprm->cred` 的 uid/gid/caps，再把 cred SID 写成 kernel(1) |

关键点：**全程在内核里完成**，App 看到的只是一个普通文件 exec，所以
不需要 SELinux permissive、不需要 overlay/mount、不需要打策略补丁。

## 2. 为什么 `su_path` 落在 App 自己的 lib 目录

```
/data/app/~~<hash>/com.dsh.ppgroot-<hash>/lib/arm64/libksu_su.so
```

该路径的标签是 `apk_data_file`，而 SELinux 的规则是

```
allow untrusted_app apk_data_file:file execute      # 类型级，不是按包名
```

这是 App 能跑自己 native 库的机制，所以**任何 App 都能 exec 任何 apk_data_file**。
loader 用 `pm path com.dsh.ppgroot` 现算路径（`~~hash` 每次安装都变），把 ksud 复制过去并 `chmod 755`
（APK 解出的库默认 0644，没 x 位 exec 会 EACCES），再作为模块参数 `su_path=` 传给 ko。

实测标签正确：

```
[su] 目标=/data/app/~~uDiM2U1z3kYceYut47ibYw==/…/lib/arm64/libksu_su.so 标签=u:object_r:apk_data_file:s0 大小=5720304
```

## 3. 实测证据（3.16.11 / ko art12）

```
ksu: su-exec kprobe rc=0 path=/data/app/~~uDiM2U1z3kYceYut47ibYw==/…/lib/arm64/libksu_su.so
ksu: exec-entry kprobe rc=0
ksu-dbg XEC: uid=0 name=/system/bin/cat / find / sleep …          ← do_execveat_common 真被调用
ksu: su-redirect uid=11207 /system/bin/su -> /data/app/~~uDiM2U1z… ← 管理器 exec su 时改写成功
```

三条合起来证明：**kprobe 挂得住、文件名改得掉、App 侧确实命中**。
之前怀疑的「LTO 把 `do_execveat_common` 内联掉」被这组日志排除。

## 4. 已知限制：shell 侧测不出来

`adb shell su -c id` 一直是 `inaccessible or not found`，原因不是改写失败，而是
**shell 的 execvp 会先做存在性检查**，`/system/bin/su` 这个文件根本不存在，检查不过就不 `execve`，
钩子自然收不到。`toybox env su` 报 `exec su: No such file or directory` 同理。
KSU 原生还要伪造 `faccessat`/`newfstatat`，正是为这类预检；我们这版没做，所以验收要靠 App 侧命中
（管理器 uid=11207 那次就是活样本）。

## 5. 步骤②的实现要点

* `begin_new_exec()` 里紧接着就是 `security_bprm_committing_creds()` 和 `commit_creds(bprm->cred)`，
  在它的 pre_handler 里改 `bprm->cred` 字段，等于让新程序直接以 root 启动；
  **全是已有结构体的字段赋值**：不分配、不 sleep —— 这正是之前 `prepare_creds()`（GFP_KERNEL）走 kprobe 会炸的反面。
* SID 不能在同一个 pre_handler 里改：`security_bprm_committing_creds()` 会用策略结果覆盖。
  改用 kretprobe 挂在它后面，把 `cred->security`（`task_security_struct`，头两个 u32 是 osid/sid）的 sid 写成 1（kernel）。
* 认领方式：重定向成功时记 `ksu_su_pid = current->pid` + `jiffies`，5 秒内 `begin_new_exec` 认领；不依赖 `bprm->filename` 字符串比较。
* kretprobe 的 `entry_handler` 里必须把 `bprm` 存进 `ri->data` —— 返回时 `regs->regs[0]` 已经被返回值占用了。

## 9. 吸收自《CVE-2026-64560 技术报告（脱敏版）》

那份报告是另一个平台（SM8850 / 6.12.58）的 posix-cpu-timers UAF 链，漏洞本身借不过来，但工程教训有六条能直接用：

| # | 教训 | 落地情况 |
|---|---|---|
| 1 | **符号清单与模板必须双向校验**：`PATCHED=N MISSING=0` + `undefined not in syms=[]` + `syms not undefined=[]`。清单缺一条，patch 工具就整体 ABORT | 已写成 `D:\ksu-build\ko_check.py`：打包前跑，逐份 ko 校验「UND 全部在清单里 / vermagic / 本轮改动的字符串真的进包了」。用它复检 art13 立刻抓出 `jiffies` |
| 2 | **ksud 必须与 ko 同源**：Next 的 ksud 配官方 ko → `os error 2`，还会把 `/data/adb/ksud` 搞坏 | loader 的 `_su_setup_apk` 改为优先 `${RD}/ksud_mgr`（从用户选中的管理器 APK 里抽的 libksud.so），回退 `ksud_resukisu` / `ksud_success`，并先调 `_extract_mgr_ksud` |
| 3 | root 进程的上下文用 `u:r:ksu:s0`，不是 kernel | 待验证：步骤② 现在写 `SECINITSID_KERNEL(1)`，等 3.16.13 真机日志看 `id` 报的 context 再决定是否改成 ksu 的 sid |
| 4 | **APK 的 edge-to-edge / 旋转丢日志** | 本工程已具备：manifest 两个 Activity 都有 `configChanges="keyboardHidden|orientation|screenSize"`，根布局 `fitsSystemWindows="true"`，主题 `Theme.Material.NoActionBar` |
| 5 | adb 挂起与 `pkill` 自匹配（`-T`、`</dev/null`、`nohup setsid`、`[t]64560` 括号技巧） | 主机侧临时脚本沿用，未固化 |
| 6 | **残留与 ETXTBSY**：旧二进制还在跑时重新部署会 `ETXTBSY/EPIPE` | `_su_setup_apk` 改为「先写 `libksu_su.so.new` 再 `mv -f`」——rename 不受忙碌文件影响 |

不适用（我们换了实现）：KASLR raw-trace 投票（我们能用 kallsyms）、perf 采 cred + CapBnd 门闩（我们 cred 由 exploit 直接改写）、`track_throne` 改 `&init_cred`（我们用 setresuid kprobe 加冕）、BTF 提偏移（我们改的是 `bprm->cred` 指针）。

一个对照：那条链是概率性的（1/1000–1/5000 次 exec，命中未抢页就 panic），我们的 kprobe 方案只要模块装上就是确定性行为；真正卡我们的始终是「模块装不上」这类工程问题。

## 10. 阶段归档（3.16.12 → 3.16.21，六次翻车五次在打包环节）

这一轮把「su 到底能不能用」拆成了三层，逐层证伪，最后收敛到两个真问题。

### 10.1 三层结构

| 层 | 做什么 | 现状 |
|---|---|---|
| ① 文件名改写 | `do_execveat_common` 里把 `fn->name` 原地覆盖成 App lib 目录里的 ksud 副本 | ✅ 稳定（6 次重定向零崩溃） |
| ①.5 access/stat 伪装 | `faccessat`/`faccessat2`/`newfstatat`/`statx` 把路径参数写进用户栈下方再改指针 | ✅ 钩子挂上（rc 全 0），待有真实调用方 |
| ② 换身份 | `begin_new_exec` 改 `bprm->cred`；`su_cred=2` 走 task_work → `escape_with_root_profile()` | ① 已验证 uid 0；域仍是 `untrusted_app` |

### 10.2 六个坑逐条

1. **`kfree(fn->name)` 会 panic**（3.16.16 现场）：短路径时 `getname_flags()` 把名字放在 `struct filename` 内嵌的 `iname[]` 里，`fn->name` 是结构体内部指针，`kfree` 属非法释放 → 破坏 slab，过一阵才崩。改成原地 `memcpy`（先判 `strlen < PATH_MAX`），同一路径连跑 6 次零崩溃。
2. **`kfree` 之外还有一处野写**：kretprobe 里 `*(u32*)((char*)cred->security + 4) = 1` 盲写 SELinux 私有结构体，已整段删除；换域改用 KSU 自己的 `escape_with_root_profile()`（它 `setup_selinux()` + `alloc_uid()` + `set_cred_ucounts()`，手工写必漏）。
3. **kprobe 里不能调 `escape_with_root_profile()`**：`prepare_creds()` 是 `GFP_KERNEL`，kprobe 在 arm64 `brk` 异常上下文里，睡就 BUG。改法：kprobe 只 `task_work_add(TWA_RESUME)`，回调在 `exit_to_user_mode` 前跑（普通进程上下文，可睡），此时 exec 已完成、新程序第一条指令未执行。
4. **`su` 报 `inaccessible or not found` 且钩子 0 命中**：因为 aShell 的 root shell **自己已经是 uid 0**，从它敲 `su` 时调用方 uid=0，被我们的门控（只放行 allowlist 和管理器）挡掉。门控加 `u == 0`。
5. **`unsupported RELA relocation: 312`**：给 `escape_with_root_profile` 加 `__attribute__((weak))` 后编译器走 GOT，产生 `R_AARCH64_ADR_GOT_PAGE(311)`/`LD64_GOT_LO12_NC(312)`，而内核模块加载器不建 GOT → insmod 失败、模块根本没装载（于是「管理器没有自动加冕」只是表象）。改普通 `extern`（同 ko 内定义，直接调用）。
6. **`ko_patch2` 的清单是硬约束**：`jiffies`、`ksu_manager_appid` 两次都是清单外 UND → 整链 ABORT。

### 10.4 运行时开关（都写在 `/sys/module/kernelsu/parameters/`）

| 参数 | 含义 |
|---|---|
| `su_cred=0` | 只重定向，不动 cred |
| `su_cred=1` | 手工写 `bprm->cred`（uid 0 生效，域不变） |
| `su_cred=2` | task_work → `escape_with_root_profile()`（uid + 域 + caps 一起） |
| `su_check=0` | 关掉 access/stat 伪装 |
| `su_mgr_appid` | 放行管理器自身 uid |
