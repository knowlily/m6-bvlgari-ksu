# 2026-10-26 · 灭屏整机复位结案：exploit 孤儿在 CPU0 自旋 → RCU stall → PMIC 断电

设备：Honor BVL-AN16（Magic6 Pro）· MagicOS 10.0.0.170 / Android 16 · 内核 `6.1.157-android14-11-g7d3922fade43`

## 症状

提权成功后（`kernelsu … Live`），**熄屏**放着 20 秒 ~ 20 分钟，整机像被拔电池一样复位。复位后：

- `pstore` / `console-ramoops` 全空
- `dropbox` 只有 `SYSTEM_RESTART`
- `dmesg` 里 `Kernel panic 0`、`BUG 0`、`Oops 0`、`hung task 0`
- **不熄屏就没事**

## 真正的元凶

把 `cat /dev/kmsg` 采集进程从 **`u:r:ksu:s0` 的 root shell** 里起（loader 自己起的采集器每次都在 `insmod` 那一瞬死掉，会伪造“内核没了”的假象），抓到 2.95 MB / 24800 行完整日志，末尾是：

```
rcu: INFO: rcu_preempt detected expedited stalls on CPUs/tasks: { 0-.... } 21433 jiffies
rcu: blocking rcu_node structures (internal RCU debug):
Task dump for CPU 0:
task:cve-2026-43499-  state:R  running task  stack:0  pid:1894  ppid:1  flags:0x0400040b
Call trace:
 __switch_to+0x194/0x324
 0x22400005
```

Honor 自己的 hangdetect 同段印证只有 0 号核异常：

```
hangdetect_cpu_: bind_task_check hangdetect bind task fail, kick_bits: 0x7e, check_bits: 0x73
CPU 0 … state 0      ← 被占死
CPU 1..7 … state 64  ← 正常空闲
```

**exploit（`cve-2026-43499-bin-dc14`）成功后没退干净**：父进程退出，残留进程被 init 收养（`ppid:1`），在 CPU0 上空转（`state:R`）。后果链：

1. RCU expedited grace period 永远完不成 → `expedited stalls`
2. 灭屏 suspend 要冻结全部任务并等 RCU → 冻结卡死（日志停在 `Freezing user space processes` 后 1.4 秒）
3. Honor `hangdetect_userpet` / PMIC 硬件看门狗发现喂狗停了 → **直接掉电**
4. 外部看门狗断电不是内核 oops ⇒ pstore / ramoops / dropbox 全空，`dmesg` 一个 panic 都没有

## 走错的几条路（都排除）

| 假设 | 为什么不对 |
|---|---|
| `core_hang_detect`（PMU + qcom-scm 平台复位） | 2.57 已把 `/sys/devices/system/cpu/hang_detect_core/enable` 写 0，照样复位 |
| `bootfail` 看门狗 | `boot_detector_enabled` 由 `Y` 改 `N` 后照样复位 |
| suspend freeze 全局死锁（KernelSU 钩子锁） | 冻结卡住是**结果**：RCU 走不完，冻结自然等不到 |
| `sucompat` execve 钩子 | 关掉（`force_feature=su_compat:0`）照样复位 |
| FinaSU `mount_view_filter` ABBA 死锁 | 换 FinaSU v1.2.1 照样复位 |

## 修复

loader 2.62 起在装载流程加 `_sweep_orphans()`，只用 shell 内建（`read` + `kill`），不 fork/exec，所以装载后 execve 全废也能跑：

```sh
for _pp in /proc/[0-9]*; do
  read -r _pc < "$_pp/comm" 2>/dev/null || continue
  case "$_pc" in
    cve-2026-43499*|kaslr_leak*|poison_hunt*|poison_trap*) kill -9 "${_pp#/proc/}" ;;
  esac
done
```

装载前 / 装载后 / 收尾 / Live 复用分支，共 4 处调用。首轮实测：

```
[clean] kill -9 13008 (cve-2026-43499-)
[clean] kill -9 13045 (cve-2026-43499-)
[clean] kill -9 19776 (cve-2026-43499-)
[clean] 本轮清理 3 个 exploit 孤儿
```

之后长时间灭屏不再复位。

## 附带结论：`sucompat` 可以永久关闭

同一轮 `force_feature=su_compat:0`：

```
feature get su_compat → Value: 0 / Status: disabled / Forced: by boot config
app 内 su -c id       → uid=0(root)，进程上下文 u:r:ksu:s0
```

说明 root 走的是 **`su_path=/dev/su` + `su_cred=2`**：授权应用 exec 预置的 ksud（`/dev/su`），内核换 root 凭据并 `escape_with_root_profile` 换域。**与 `execve("/system/bin/su")` 重定向无关**，FinaSU v1.2.1 同样如此。

⇒ 默认不传 `WANT_SUCOMPAT`：少一个 execve 热路径钩子，隐藏性和稳定性都更好，su 照常可用。

## 自查清单

```sh
# 1) 有没有孤儿（应为空）
for p in /proc/[0-9]*; do c=''; { read -r c < $p/comm; } 2>/dev/null; \
  case "$c" in cve-2026*|kaslr_leak*|poison_hunt*) echo "$p $c";; esac; done

# 2) 起采集（root shell 里，loader 自己起的那种会死在 insmod）
su -c 'nohup cat /dev/kmsg > /data/local/tmp/route/m6/kmsg3.txt 2>/dev/null &'

# 3) 灭屏 30 分钟后
grep -c "expedited stalls" kmsg3.txt   # 应为 0
```

## 教训

1. **“没有 panic 记录”不等于不是内核问题** —— PMIC / `qcom-scm` 外部断电不留任何内核痕迹。
2. **“只在灭屏时炸”不等于和 suspend 有关** —— suspend 只是放大器。
3. **日志采集器必须活在不受影响的域里** —— 它自己死在装载那一刻，会把“内核死了”喂给你。
4. **exploit 的残留进程要主动收尸** —— 别指望它自己退出。
