# 2026-10-27 · 提权成功率：三条"根因"被证伪，真信号只有一个

设备：Honor BVL-AN16（Magic6 Pro）· MagicOS 10.0.0.170 / Android 16 · 内核 `6.1.157-android14-11-g7d3922fade43`
仓库分工：本仓库只放内核/ko 侧结论；脚本侧细节见 `m6-jailbreak-core/docs/07-privilege-success-rate.md`

## 背景

用户反馈「提权成功率太低」。当时手上**只有成功日志**，没有失败样本。
于是先把日志里所有 `[-]` 行都当嫌疑，先后得出三条"根因"，全部在真机上被证伪。

## 被证伪的三条

### ① `resize_pipe_slots soft-fail … errno=1 cur=8192`

反汇编 `resize_pipe_slots`（`0x1a35c`）：

```asm
mov w1, #0x407   ; F_SETPIPE_SZ，w20 = slots<<12 = 131072B（32 页）
bl  fcntl
mov w1, #0x408   ; F_GETPIPE_SZ，失败时读回来当 cur 打印
bl  fcntl
```

⇒ `cur=8192` 是**这个管道自己的大小**（2 页），不是整用户配额用量。

真机读到的 sysctl（loader 拿到 root 后）：

```
[pipeq] pipe-user-pages-soft=0      # 0 = 关闭软限制
```

而成功轮 `dc270.log` 有 **129 次** soft-fail 仍然 `attempt=1 verified=1 step=0`。
结论：这条路**不可追**。

### ② `slide pselect cannot place … global_word=21 nfds=320`

按 `words_per_set = nfds/64 = 5`、目标 word = 21 推断"几何放不下"，算出 `nfds = (21+2)×64 = 1472`。

但成功轮（同一设备，换了个 boot）里有 **4 条** `cannot place`，照样 `step=0`：

```
[-] slide pselect cannot place ww_ctx waiter_word=10 global_word=21 words_per_set=5 nfds=320
[*] app fops slide attempt=1/8 triggered=1 verified=1 step=0 errno=0
```

⇒ 它有回退路径，`cannot place` 只是单路记录。

### ③ "同 uid 管道页被占满"

`[pf] 同 uid 管道：本套件残留=2 其它=8` —— 全 uid 才 10 个 pipe fd。
数量级差两个数量级，不成立。

## 反面证据：调大 nfds 会硬复位

按错误推断写入 `SLIDE_NFDS=1472` 的那一轮：

```
[*] kernel page prepare attempt=5/8 base=ffffff8047d8000
[*] mm leaked=ffffff8047d87c00 object_index=31
[*] CP main: before-slide-route        ← 日志到此为止
```

约 1 分钟后整机复位，`/sys/fs/pstore/` **空**（PMIC 硬件复位，不是 panic）。

对比同等失败但 `nfds=320`：日志完整、`M6_VERDICT: MISS`、系统可继续使用。

**风险不对称**：干净失败可以重启重试，硬复位拿不到任何现场。
⇒ 自动调参默认关闭，必须显式 `touch $RD/AUTO_NFDS` 才加载，且上限夹到 1024。

## 真信号：写通道是一次性的

失败轮结尾：

```
[*] p0 physical write status=0 ok=1
[*] cfi misc_fops readback ret=8 val=ffffffdd17ef79d0 (restored)
[*] app fops slide attempt=1/8 triggered=1 verified=0 step=8 errno=0
[+] pipe physrw pid=13632 done=0 root=0 kaslr=1 read_ok=0 write_ok=0
[!] stack writer ran; refusing retry on this boot
```

写执行了、`misc_fops` 也复原了，但 physrw 没立起来（`step=8`），exploit 拒绝本 boot 重试。
此时**再跑多少次都不可能成功**，唯一处置是重启换 KASLR slide。

脚本侧 2.76 起据此写 `$RD/NEED_REBOOT`。

## 真干扰项：旧守护吃半个核

`/proc/<pid>/stat` 两遍采样（8 核满窗口 = 1600 tick / 2s）：

```
   495  sh   pid=18971    ← 49.5% of one core
    59  sh   pid=23154
    34  system_server
```

`18971` 是 loader 自己 spawn 的 `bfm_watch` 循环，**每秒 fork 三个外部命令**（`cat`/`echo`/`echo`），
日志还写在旧版本路径 `/data/local/tmp/ksu/`，跨了好几轮都没退。

对 KernelSnitch 是直接干扰（靠 CPU 计数器测碰撞，边上持续被抢核）。
改法：内建 `read` 取值 + 每 5 秒一轮 + `BFM_WATCH_MAX` 轮后自退，并在装载前
`_reap_legacy_daemons` 清掉历史实例（只匹配守护特征串，**不要**匹配 `route/m6`，会杀掉自己）。

## 认知层面的三条教训

1. **`[-]` 行不等于失败原因** —— 先在成功日志里搜一遍，出现即噪声。
2. **对比两份日志的交集**：本次真正的线索（`refusing retry`）是"只在失败轮出现"的那一行。
3. **改 exploit 参数前先问失败代价**：默认 320 是干净失败，1472 是硬复位。

所有改动都在脚本侧（`dc_ksu_run.sh` / `ksu_loader.sh`，版本 2.67→2.76），
