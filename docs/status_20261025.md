# 2026-10-25 状态：panic 排查与 sucompat 默认关闭

## 一、结论先行

1. **这台机器的 `su` 不依赖 sucompat。** ko 把 `su_path`（`/dev/su`，7,452,064 B = FinaSU v1.0.10 的 ksud）
   注入成真实文件 `/system/bin/su`，走 Honor 自己的 overlay：
   ```
   overlay on /system/bin  lowerdir=/patch_hn/overlay/system/bin:/system/bin
   -rwxr-xr-x 1 root root 7452064 <run 时刻> /system/bin/su
   ```
   App 直接 `execve("/system/bin/su")` 就能跑，不需要内核钩子。
2. **sucompat 是多余且危险的**：它直接改 `pt_regs` 再跳 `execveat`（`fsu10/kernel/feature/sucompat.c:187-288`），
   本机（荣耀 6.1.157 + CFI + `override_creds=off`）上装载后 `exec` 立刻 `rc=139`（SIGSEGV），
   全系统进程起不来；上一轮 panic 发生在装载后 27 分钟。
3. **2.25 起 sucompat 默认关闭**（`force_feature=su_compat:0`）。要恢复：`touch $RD/WANT_SUCOMPAT`。

## 二、A/B 实测

| 组 | 配置 | 装载后 exec | 结果 |
|---|---|---|---|
| 对照 | `force_feature=su_compat:0`（2.24 前是数字 `0:0`，按源码等价） | loader 自己 `rc=127`（普通失权） | 模块 Live **27.6 分钟无 panic**，aShell `su -c id` 正常 |
| 复现 | sucompat 默认开（12:09 那轮，2.20） | `rc=139` + 满屏 Segmentation fault | 装载后 **27 分钟 panic** |

判据差异只在 `do_execveat_common` 上的钩子。

## 三、排查过程中被推翻的假设

| 假设 | 证伪方式 |
|---|---|
| `next_sym_addr_uapi5.txt` 过期 ⇒ ko_patch2 把 240 个符号 patch 到错地址 | 用「kallsyms 名字顺序」做交叉校验：271 条里 270 条存在于本机、按清单地址排序后 kallsyms 序号**零逆序** ⇒ 清单是本机生成的 |
| 2.16 没传 `su_path` 所以 su 是死的 | 用户实测 2.16 aShell `su -c id` = uid=0；且 su 来自 `/system/bin/su` overlay，与 su_path 无关 |
| `SUCOMPAT_OFF` 文件就是关闭开关 | 假开关：真正传参的是 `NO_SUCOMPAT`/`FORCE_FEATURE`，那个文件只是 loader 自己 `touch` 的标记 |
| 关屏 panic 来自 `mount_view_filter` 的 ABBA 死锁 | v1.0.10 已修（`down_read_trylock`），当前 27.6 分钟对照组未复现；留作后备假设 |

### 结论先行

| 管理器 | APK | ksud 版本串 | uapi | 配哪份 ko |
|---|---|---|---|---|
| BakaSU | `BakaSU_v4.2.0-rc3_35252-arm64-v8a-release.apk` | `4.2.0-rc3-81-gd5e9e025` | **6** | `kernelsu_basu420.ko`（main@d5e9e025 编） |
| SukiSU | `SukiSU_v4.2.1-r2.apk` | `4.2.1-r2` | 6 | `kernelsu_suki421.ko` |

### 两个坑

**① BakaSU 的 uapi 不等于 tag 的 uapi。**
`uapi/supercall.h` 在 tag `v4.2.0-rc3` 上是 `KERNEL_SU_UAPI_VERSION = 4`，
但在 `main`（`d5e9e025`）上是 `6`。35252 这个 APK 的 ksud 版本串是
`4.2.0-rc3-81-gd5e9e025` —— `git describe` 语义为「tag 之后 81 个提交」，
所以它编自 **main**，管理器界面显示的也是 **6**。
⇒ 按 tag 编出来的 uapi4 ko 配它必然报「需要更新内核」。

**② SukiSU 发行版会改包名和 ksud 的 .so 名。**
`SukiSU_v4.2.1-r2.apk.1` 那份是被人重打包过的：包名随机（`rqglxo.qzizju.uholjr`），
ksud 改名成 `libscibhqvpwg.so`。原版 `SukiSU_v4.2.1-r2.apk` 包名仍是
`com.sukisu.ultra`，但 ksud 一样被改名（`libeexgslcpwg.so`）。
⇒ 选 ko 不能靠包名，要靠 **ksud 里的版本串**；抽 ksud 不能靠固定文件名，
要靠「arm64-v8a 下最大、>2MB 且 ELF magic 正确」的兜底（loader 早就有这条）。

### CI 侧修复：BakaSU Kbuild 硬门禁

tarball 方式集成源码时，BakaSU 的 `kernel/Kbuild` 会直接 error：

```
-- Can't find ReSukiSU git submodule!
../drivers/kernelsu/Kbuild:68: *** You should use ReSukiSU as a git submodule instead of copying code directly.  Stop.
```

门禁是这一行：

```makefile
LOCAL_GIT_EXISTS := $(shell test -e $(KSU_SRC)/../.git && echo 1 || echo 0)
```

tarball 解出来没有 `.git`。修法是在 `KernelSU/` 里就地初始化（`KSU_VERSION` 还要
`rev-list --count HEAD`，`KSU_TAG_NAME` 还要 `describe --tags`，所以两样都补）：

```bash
( cd KernelSU && git init -q . && git add -A \
  && git -c user.email=ci@localhost -c user.name=ci commit -qm "ci: tarball snapshot" \
  && git tag -f v4.2.0 )
```
