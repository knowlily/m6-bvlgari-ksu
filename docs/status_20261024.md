## 四、su 已通（2026-10-24 实测）

授权过的 App（aShell）里：

```
su -c id  →  uid=0(root) gid=0(root) groups=0(root) context=u:r:ksu:s0
```

sucompat 正常：`execve("/system/bin/su")` 被内核换成 `su_path`
（`<app lib>/libksu_su.so`，`apk_data_file`），授权由管理器名单决定。

**⚠ 测试方法上的坑**：`adb shell` 是 uid 2000，不在 allowlist ⇒ 那里 `su` 永远 ENOENT。
用 adb 测 su 会得到假阴性，2026-10-24 一度据此误判"sucompat 与厂商内核不兼容"。
正确做法：装 aShell → 管理器里授权 → 在 aShell 里敲 `su -c id`。

### 2. 装载后本进程失权（已部分绕过）

t+0 之后 `open/exec/access` 全线失败（`can't open /proc/modules: Permission denied`、
`Segmentation fault` / `rc=139`）。原因是 loader 以 exploit 伪造的 `u:r:kernel:s0` 运行，
模块一装、policy 一注入，这个伪造 SID 就失效。

绕过办法：把 su 落点、`/data/adb/ksud` 全部改到 **insmod 之前** 准备（2.6/2.7 已做）。
2.5 引入的 root watcher 实为死代码（同样失效），保留无害。

### 3. FinaSU v1.0.9 与本内核兼容性存疑

v1.0.8 的表现是 access/stat 被拒；v1.0.9 新增 `mount_view_filter`（+470 行，hook `seq_show`/`open`）
后升级成 SIGSEGV —— 与「钩子按编译期结构偏移访问 `linux_binprm`/`vfsmount`，与厂商树对不上」吻合。
**待证**：`dmesg | grep -i kernelsu` 看 `pc` 是否落在模块区间；pstore 有上次崩溃记录。

## 六、操作要点（踩过的坑）

- 一轮 boot 只能打一发（`run.lock`），换 ko 必须重启；`ksud unload` 必 panic
- 改 `versionCode` 才会改 `PAYLOAD_STAMP`；只改代码不改 vc 会跳过推送
- 载荷变了必须跑 `m6-jailbreak-core/tools/rebuild_manifest.py --sync`
- ko 体积校验以**字节数**为准（`ko_patch` 会就地改 symtab，md5 必变）
- 每轮先 `cp` 到 `.run_<name>.ko` 再 patch，否则 slide 会叠加
- 测试用 aShell 本地 shell（uid 10244）；`u == 2000` 在钩子里明确跳过
- 设备 adb 连接不稳，掉线时 `kill-server/start-server` 或让用户插拔线；
  **不要** `adb reboot` 前不问用户

## 八、2.13 / 2.14 真机验收（2026-10-24 晚）

### 起因：老壳 3.16.35 的三个兜底

老壳 3.16.35 的 `_su_setup_apk()` 里，`pm path com.dsh.ppgroot` 取不到就整体 `return 0`
⇒ `/dev/su` 不生成 ⇒ 所有 App 的 `su` 不可用。根因是 **loader 跑在 exploit 伪造的
`u:r:kernel:s0` 域里，`pm` / `cmd package` / `dumpsys` 全部空返回**。
它的修法很直接：再加一路 `/data/app` 目录 glob（目录名就是包名，不经过 PackageManager）。

2.13 把这条思路搬进 m6-shell，落了四处：

| # | 函数 | 之前 | 现在 |
|---|---|---|---|
| 1 | `_detect_mgr_pkg()` | `pm list packages` 空就 `return 1` ⇒ 永远识别不到管理器 ⇒ 退回 uapi5 `kernelsu_custom.ko` | 空则 `ls -d /data/app/*/<pkg>-*/`；优先级改成 fina → sukisu → weishu → next → bakasu → resukisu |
| 2 | `_self_apk_path()` | `pm path` → `cmd package path` → `dumpsys` | 再兜一层 `/data/app/*/<pkg>-*/base.apk` |
| 3 | `_su_setup_apk()` 的 `_lib` | 只认 `SELF_LIB` / `_self_apk_path` | 都失败时 glob 到 `…/lib/arm64` |
| 4 | `_pick_custom_ko()` 的"管理器是否已装" | `pm list packages \| grep` | 加 `/data/app` glob |

### 2.14：修掉一条假的告警

2.13 日志里出现：

```
[probe] su: /dev/su 不是 su 而是 ksud 本体（uapi 不匹配）
```

**这条是误报**。`su` 前端按 `argv[0]` 的 basename 判断模式（`basename == su` ⇒ su 分支），
而 probe 直接跑 `/dev/su -c 'id -u'`，某些 ksud 构建仍走 CLI 解析 → 打印 `Usage: su <COMMAND>`
→ 命中旧的正则。同一轮 App 域里 `su` 完全正常。

2.14 改成先用**名为 `su` 的软链**（`$RD/.su_probe/su -> /dev/su`）再跑，并把结果分三档：

| 输出 | 含义 |
|---|---|
| `rc=0 uid=0` | su 真的放大成 root |
| `rc=0` 非数字 | 前端能跑但没换权（调用者不在 allowlist，属正常） |
| 打印用法 / ENOSYS | 前端没接通（这时才该怀疑 sucompat） |
